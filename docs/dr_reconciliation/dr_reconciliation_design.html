DR Reconciliation — Architecture & Build Spec

Implementation-grade design for the recon engine + AI/BI dashboard · Databricks Managed DR · AWS

This is the developer-facing companion to the sample dashboard. It specifies exactly what to build: the components and where they run, the end-to-end data flow, the per-object reconciliation logic (source → signature → diff → status), the control-table schemas the dashboard reads, the classification rules, the failover/failback behavior, and an ordered build plan. Everything is SDK/SQL-only and reads the read-only secondary through a monitor workspace — no compute runs on the passive side.

End-to-end pipeline

one run = these six stages, per failover group
STAGE 1

Resolve scope

Determine the expected in-scope inventory for the failover group.

DR REST API failover groups; system.replication.states.managed_assets
scope: catalogs[], workspace_sets[], rpo_target
STAGE 2

Read primary

Collect the primary-side signature for every in-scope object of the top-10 types.

information_schema · DESCRIBE · Jobs/Warehouse/Cluster/Workspace/permissions API
primary_sig per (object_type, fqn)
STAGE 3

Read secondary

Same reads against the read-only secondary via the monitor workspace.

monitor-workspace client (host+token) · secondary metastore
secondary_sig per (object_type, fqn)
STAGE 4

Diff & classify

Compare signatures per object; fold in Managed-DR errors + the silent-gap set.

primary_sig, secondary_sig, states.errors[], unsupported set
status ∈ {IN_SYNC, LAGGING, DRIFTED, MISSING, FAILED, UNSUPPORTED} + severity
STAGE 5

Persist

Write the run summary, coverage rollup, per-object inventory, and findings.

classified objects + run metrics
MERGE → dr_recon_runs / _coverage / _inventory / _findings
STAGE 6

Publish & alert

Dashboard reads the tables; alert on regression (new MISSING/FAILED, RPO breach).

dr_recon_* tables
AI/BI dashboard refresh · alert to SQL alert / webhook

Signatures, diff & classification

how a status is decided — apply in precedence order
Classifier — precedence (first match wins)
# inputs: in P?, in S?, states_error?, unsupported?, lag_ms, target, sigP, sigS
def classify(o):
  if o.unsupported_in_scope:      return "UNSUPPORTED"  # silent gap
  if o.states_error:             return "FAILED"       # DR_* error class
  if o.in_primary and not o.in_secondary: return "MISSING"
  if o.lag_ms is None:            return "MISSING"   # never replicated
  if o.sigP != o.sigS:           return "DRIFTED"
  if o.lag_ms > o.target_ms:      return "LAGGING"
  return "IN_SYNC"
severity: MISSING/FAILED → CRITICAL · grants/ACL DRIFT → WARNING+ · LAGGING → WARNING · UNSUPPORTED → INFO
Readiness rollup (per run)
GREEN   scope fully covered, 0 MISSING/FAILED,
        0 blocking errors, lag ≤ target
AT_RISK any DRIFTED/LAGGING, or lag > target,
        but nothing MISSING/FAILED
CRITICAL any MISSING or FAILED object, or a
        blocking error, or lag = null

6

Failover / failback behavior

how recon behaves around DR events — direction is data-driven from states.effective_primary_region
Steady state (primary = east)

Engine reads east as primary, west (via monitor) as secondary, on the schedule. Readiness answers “if east fails now, is west a faithful, complete replica?”. RPO trend tracks replication_lag_ms.

On failover (east → west)

Managed DR flips effective_primary_region to us-west-2 and reverses replication. The engine auto-detects the flip and reconciles in the new direction (west = primary, east = secondary). It records a FAILOVER DR-event row with the data-loss window (lag at cutover) vs RPO.

Failback (west → east) & reconciliation

After east is restored and made primary again, the engine reconciles west → east and reports which objects changed while west was primary and whether they made it back to east — the failback reconciliation. The DR-events table logs each promotion, its duration, data-loss window, and “objects reconciled N/M”.

Drills

A planned failover+failback pair should end GREEN with a 0s data-loss window. The dashboard’s “Last DR test” KPI + DR-events table are the audit evidence for periodic (e.g. quarterly) DR tests.

8

Build plan

ordered milestones for the developer agent
  1. Control tables — create dr_recon_runs / _coverage / _inventory / _findings (see sql/dr_recon_tables.sql). Pick a catalog with managed storage per workspace.
  2. Scope resolver — read DR REST API + system.replication.states → in-scope catalogs + workspace sets + RPO target + errors[]. Emit the expected inventory.
  3. Primary readers — one per object type (Stage 2 sources). Return {fqn: primary_sig}. Start with the 7 workspace-asset types (priority), then the 3 UC types.
  4. Secondary readers — same readers pointed at the monitor workspace / secondary metastore. Reuse the primary reader code with a different client.
  5. Differ + classifier — per-object signature compare → status + severity (Section 4 precedence). Fold in states.errors[] and the unsupported set.
  6. Control writer — MERGE run summary, coverage rollup, inventory, findings. Idempotent per run_id.
  7. Scheduler — Asset Bundle job on the RPO cadence; direction auto-detected from effective_primary_region.
  8. AI/BI dashboard — build over the control tables (KPIs, scorecard, RPO trend, errors, drill-down). The sample HTML is the visual spec.
  9. Alerting — SQL alert / webhook on new MISSING·FAILED, RPO breach, readiness ≠ GREEN.
  10. DR-event hooks — record FAILOVER/FAILBACK rows + post-event reconciliation (Section 6).
